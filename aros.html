Project Overview

What AROS Does

A runtime behavioral drift detection framework that monitors Windows services, learns their normal operational profile, and detects long-term deviations — not just immediate anomalies.

Core Concept
Behavioral Identity Modeling
AROS treats each monitored Windows service as having a behavioral identity — a stable, multi-dimensional statistical profile derived from runtime telemetry during normal operation. Persistent, statistically significant drift from this identity triggers a security-relevant flag.
Key Differentiator
Not Just Another IDS
Traditional IDS systems look for sudden, known-signature events. AROS detects gradual departure from a service-specific behavioral baseline over long time windows — weeks or months of stealth, not seconds. The novelty is in temporal persistence, not pattern matching.

Phase 1 Scope — Implemented

Windows runtime telemetry collection (ETW, Sysmon, Perf Counters)
Multi-dimensional behavioral baseline modeling
Statistical distribution comparison & drift scoring
Drift persistence analysis across time windows
Controlled evaluation with four defined metrics
Structured alert logs & drift score visualizations
Literature survey & architecture documentation

Research Gaps

Six Identified Gaps (G1–G6)

G1
Real-Time Bias in Detection Systems
Existing IDS analyze discrete events or short time windows — optimized for sudden attacks but blind to threats evolving over days or weeks. Long-term behavioral drift falls entirely outside their detection horizon.
G2
Absence of Behavioral Identity Modeling
No current tool models the behavioral identity of a specific software service. Generic thresholds and network-layer signatures cannot distinguish legitimate workload variation from security-relevant drift.
G3
Lack of Drift Persistence Analysis
Statistical anomaly tools evaluate each time window in isolation — they cannot determine if a deviation is transient (a maintenance task) or persistent (a backdoor gradually increasing outbound traffic). High FPR results.
G4
Windows Runtime Security Under-Addressed
Most research targets Linux or cloud-native environments. Windows-based systems — dominant in enterprise settings — receive comparatively little behavior-centric security research attention despite rich telemetry availability.
G5
No Integrated Detect–Analyze–Evaluate Pipeline
Existing research isolates single aspects: feature engineering, ML model accuracy, or system overhead. No integrated pipeline exists from telemetry collection through drift quantification with measurable outcomes in a controlled Windows environment.
G6
Recovery Without Detection Foundation
Self-healing and adaptive recovery are active research areas, but the foundational problem — accurate behavioral drift detection as a prerequisite for meaningful recovery — remains underexplored for Windows runtime service-level monitoring.
System Design

5-Layer Architecture Pipeline

Modular, sequential design — each layer independently testable before integration. Data flows one-way with a feedback loop for baseline refinement.

1
Layer 1 — Collection

Telemetry Collection Module

Lightweight agent deployed on the target Windows host. Interfaces with ETW providers, Sysmon event channels, WMI performance counters, and Windows Event Logs. Samples at configurable intervals (default: 10s). Produces timestamped feature vectors for each collection window.

ETWSysmonWMI CPU · Memory · Process · Network · Timing
2
Layer 2 — Preprocessing

Pre-processing & Feature Engineering

Receives raw metric time series. Applies sliding window aggregation, inter-quartile-range-based outlier filtering, and feature normalization. Computes derived features: rolling mean, variance, 95th-percentile, rate-of-change. Outputs cleaned, windowed dataset ready for modeling.

WindowingIQR Filtering NormalizationRolling Statistics
3
Layer 3 — Modeling

Behavioral Baseline Model

Ingests normal-operation dataset (observation phase). Constructs a multi-dimensional statistical profile: per-feature mean/variance, empirical distribution fits, and covariance structure. Uses Isolation Forest for outlier-resistant baseline estimation. Model is serialized for persistent comparison.

Isolation ForestDistribution Fitting Covariance MatrixProfile Serialization
4
Layer 4 — Detection

Drift Detection Engine

Compares live feature vectors against the stored baseline using Kolmogorov-Smirnov tests for distribution shift and KL-Divergence for information-theoretic distance. Computes a composite drift score. Persistence check: drift must exceed threshold across N consecutive windows before an alert is raised — preventing transient false positives.

KS-TestKL-Divergence Drift ScoreCUSUM Persistence Filter
5
Layer 5 — Analysis

Alert & Evaluation Output

Structured alert logs with timestamp, affected metrics, drift magnitude, and severity classification. Drift score timeline charts for visual inspection. Evaluation metric computation: detection latency, FPR, accuracy, and monitoring overhead. Produces the final evaluation report comparing against ground-truth drift introduction points.

Evaluation ReportDrift Timeline Metrics DashboardAlert Log (JSON)
↑ Feedback Loop: Confirmed normal-behavior windows from Layer 5 incrementally update the behavioral baseline in Layer 3, accommodating legitimate long-term evolution without compromising drift sensitivity.

Experiment Design

Controlled Test Scenarios

Scenario A — Baseline
Normal Operation Profiling
Deploy target Windows service (e.g., IIS, Windows Update). Run for 24–48 hours under representative workload. Collect telemetry, build baseline model. Verify drift score stability (M5) during this phase. No attacks introduced.
Scenario B — Gradual Drift
Configuration Drift Injection
Incrementally modify service configuration over 2–4 hours (e.g., increasing thread count, adjusting resource limits). AROS should detect the gradual behavioral shift. Measures detection latency (M1) and accuracy (M3).
Scenario C — Persistence Simulation
Simulated Backdoor Behavior
Using Kali VM, simulate a persistence mechanism that causes gradual increase in outbound network connections over hours. Transient spikes should not trigger alerts; persistent drift should. Tests persistence filter effectiveness and FPR (M2).
Scenario D — Process Lifecycle
Process Anomaly Injection
Introduce unexpected child process spawning or abnormal handle count growth. Validates that process-dimension drift is detected independently of CPU/memory features. Tests multi-dimensional baseline sensitivity.

Project Title & Problem Statement
What exactly is "behavioral drift" and how is it different from a normal anomaly? ▾
Ideal Answer

An anomaly is a single-observation deviation from expected behavior — a CPU spike, a failed login. Behavioral drift is a statistically significant, persistent shift in the distribution of behaviors over a long time window. A service whose average network connection count drifts from 12/min to 47/min over three weeks is exhibiting behavioral drift, not an anomaly. The individual observations may look normal; it's the distributional change that is the signal.

"We detect change in the distribution, not outliers within a fixed distribution."
Reviewer is testing: Whether you understand the conceptual distinction between anomaly detection and drift detection — the entire research premise.
Why target Windows specifically? Isn't the research more general? ▾
Ideal Answer

Windows is the dominant enterprise OS and has unique, rich telemetry sources not available on Linux — ETW, Sysmon, WMI Performance Counters, and the Windows Event Log ecosystem. These provide deep service-level behavioral signals. Most existing runtime monitoring research targets Linux or cloud-native environments, creating a specific gap for Windows runtime behavioral security. The platform choice is a research contribution, not a constraint.

"The Windows telemetry ecosystem is richer than Linux's for behavioral profiling at the service level. The gap in Windows-focused research is documented in our literature survey."
Reviewer is testing: Whether the Windows focus is a principled research decision or just because you use Windows personally.
Literature Survey & Research Gap
How is AROS different from Sysmon or Windows Defender ATP — they also monitor runtime behavior? ▾
Ideal Answer

Sysmon is a telemetry source — it logs events but does no analysis. Windows Defender ATP uses primarily signature-based and ML event-classification approaches designed for detecting known malware families and immediate anomalies. Neither constructs a service-specific behavioral identity profile, neither tracks distributional change across long time windows, and neither computes a drift score based on statistical divergence from a learned baseline. AROS is an analysis framework that can consume Sysmon data as input.

"Sysmon produces the raw events. AROS is what makes sense of them over time."
Reviewer is testing: Whether you know the existing Windows security tooling well enough to position your work accurately.
What is "concept drift" and is it the same as behavioral drift? ▾
Ideal Answer

Concept drift is a machine learning term describing when the statistical properties of the target variable a model is trained to predict change over time — causing the model's accuracy to degrade. Behavioral drift as used in AROS is a security-domain application of this idea: we model the normal behavior distribution of a Windows service, and detect when the live distribution diverges from it. The underlying mechanism is similar — distribution shift over time — but the context is operational security rather than supervised learning.

"Concept drift is the ML phenomenon. Behavioral drift is what it looks like in a runtime security context — the same statistical machinery, different interpretation domain."
Reviewer is testing: Technical depth in the statistical foundations of the project.
Methodology & Objectives
How do you distinguish legitimate behavioral change from security-relevant drift? ▾
Ideal Answer

This is the core challenge AROS addresses through two mechanisms. First, the persistence filter: a deviation must persist across N consecutive windows before triggering an alert — ruling out transient workload spikes. Second, multi-dimensional analysis: legitimate changes (e.g., a scheduled update task) typically affect a bounded set of features temporarily; security drift affects multiple correlated dimensions simultaneously and persistently. We acknowledge this is a research challenge and evaluate it explicitly through controlled scenarios where ground truth is known.

"Persistence across dimensions, not single-window deviation, is our detection signal. This is a fundamental design choice, not a patch."
Reviewer is testing: Whether you've thought through the false positive problem rigorously.
Why isn't self-healing in Phase 1? Isn't that the whole point of AROS? ▾
Ideal Answer

Self-healing without a validated detection foundation is dangerous — an autonomous recovery mechanism acting on false positives would cause unnecessary downtime. Phase 1 delivers the detection pipeline with rigorous evaluation metrics. The research contribution is the behavioral drift detection framework itself. Recovery is architecturally specified in Phase 1 (the five-layer design accommodates it) but not implemented, specifically to avoid overclaiming and to ensure any future recovery mechanism has a reliable trigger. This is sound research methodology, not a shortcut.

"You cannot build reliable recovery on top of unreliable detection. Phase 1 solves detection. Phase 2 builds on that foundation."
Reviewer is testing: Whether the scope decision is principled or because you ran out of time.
Evaluation & Metrics
How will you validate your drift detection accuracy if you can't run real attacks? ▾
Ideal Answer

Controlled injection experiments with ground-truth labels. We introduce drift at known time points — configuration changes, simulated persistence mechanisms via Kali VM in an isolated lab — and measure whether AROS detects them within a defined latency window. This is a standard evaluation approach in behavioral security research. The controlled lab environment is not a limitation — it enables reproducibility and removes confounding variables, giving stronger experimental validity than real-world uncontrolled testing.

"Ground-truth labels from controlled injection is stronger evidence than ad-hoc real-world testing — it's reproducible and falsifiable."
Reviewer is testing: Rigor of the experimental design and understanding of evaluation methodology.
What if your FPR target of less than 5% is not met? Does the project fail? ▾
Ideal Answer

No — the targets are research goals, not pass/fail thresholds. If FPR exceeds 5%, that is a valid research finding that motivates further investigation: tuning the persistence window parameter, refining the baseline model, or improving the multi-dimensional aggregation. A research project that reports its actual numbers and analyzes why they differ from targets produces more academic value than one that cherry-picks scenarios to hit targets. Our evaluation framework captures both what works and what needs improvement.

"Research targets frame the hypothesis. Missing them is data, not failure."
Reviewer is testing: Whether you understand the difference between research evaluation and product specification.
Feasibility & Ethics
Is this realistic for a 4-person student team in one semester? ▾
Ideal Answer

Yes. The implementation is a Python agent using standard libraries (psutil, scikit-learn, scipy) on a single Windows VM in a local lab environment. No GPU, no distributed system, no real-world network access. One monitored service, one Kali VM for drift simulation. The scope is deliberately bounded: telemetry collection → baseline modeling → drift scoring → evaluation. Each component maps to one team member's module with clear integration interfaces. The timeline covers this comfortably across 3–4 months.

"One service, one VM, local environment, standard Python libraries. The scope is bounded precisely for this reason."
Reviewer is testing: Technical planning and scope management judgment.
Are there any ethical concerns with monitoring system behavior? ▾
Ideal Answer

All monitoring is performed on machines owned and controlled by the research team in an isolated local lab. No real user data, no network traffic from external entities, no cloud infrastructure. The system is a research prototype — not deployed in a production or shared environment. Any future deployment would require system owner consent and data minimization practices. In Phase 1, the ethical footprint is equivalent to a developer running profiling tools on their own machine.

"Isolated local lab, researcher-owned machines, no external data. Ethics review scope: laboratory research prototype."
Reviewer is testing: Awareness of responsible research practices.
